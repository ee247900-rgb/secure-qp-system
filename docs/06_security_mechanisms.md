# Security Mechanisms

The table below outlines the core security mechanisms employed by the system, their purpose, and how they prevent or detect question paper leakage.

| Mechanism | Purpose | How it prevents/detects leakage |
| :--- | :--- | :--- |
| **MFA (Multi-Factor Authentication)** | Identity verification | Prevents unauthorized access even if passwords are compromised by requiring a second factor (e.g., TOTP or SMS code). |
| **RBAC (Role-Based Access Control)** | Authorization | Ensures users can only access features required for their specific role (e.g., a setter cannot compile a paper). |
| **RLS (Row Level Security)** | Data-level access control | Enforced at the database level (PostgreSQL). Ensures a user can only query rows they own (e.g., their own questions) regardless of application flaws. |
| **AES-256-GCM** | Data confidentiality and authenticity | Encrypts the compiled paper before storage. GCM mode also ensures the ciphertext hasn't been tampered with. Prevents IT/DBA leakage. |
| **SHA-256 Hashing** | Data integrity | Creates a unique digital fingerprint of the original paper. Any unauthorized modification will change the hash entirely. |
| **Digital Signature (Ed25519)** | Non-repudiation | Proves the document was generated and approved by the legitimate authoritative system, preventing spoofed papers. |
| **Shamir's Secret Sharing (SSS)** | Distributed key custody | Splits the AES decryption key into shares. Requires a threshold (e.g., 3 out of 5) to reconstruct. Prevents single-user insider threats and requires collusion to leak. |
| **HTTPS/TLS 1.3** | Secure transit | Encrypts all data moving between client browsers and the API, preventing Man-in-the-Middle (MitM) attacks. |
| **Audit Logs** | Traceability and accountability | Immutably records every system action. Allows post-incident forensics to identify exactly who did what and when. |
| **Dynamic Watermarking** | Leak tracing | Embeds the Exam Centre ID, timestamp, and user ID visually and invisibly into the decrypted PDF. A leaked physical copy can be traced back to the specific centre. |
| **Time-Based Release** | Temporal security | The server rejects any attempt to reconstruct the key or download the paper before the exact scheduled time, even if authorized users request it. |
| **Private Cloud Storage** | Secure infrastructure | Storage buckets (e.g., Supabase Storage/S3) configured with strict IAM policies to block all public access, ensuring data is only accessible via signed URLs generated by the backend API. |
